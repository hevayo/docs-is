You can exchange a token that an application already has for a new {edition.productName} token. Learn how to configure the OAuth 2.0 token exchange flow in your {edition.productName} organization. Refer to [Token exchange grant](../../../../references/iam-concepts/grant-types.mdx#token-exchange-grant) for more information on how the flow works.

Follow this guide for instructions.

## Enable token exchange in your app

Enable token exchange grant in the application that requests the new token.

:::note[Before you begin]
You need to register any one of the following application types with {edition.productName}:

- [Standard-based OIDC application](../../../applications/register-standard-based-app.mdx)
- [Mobile application](../../../applications/register-mobile-app.mdx)
- [Traditional OIDC web application](../../../applications/register-oidc-web-app.mdx)

Currently, {edition.productName} does not support the token exchange grant for single-page applications.
:::

To enable token exchange in your application:

1. On the {edition.productName} Console, go to **Applications**.

2. Open your application from the list and go to the **Protocol** tab.

3. Add `Token Exchange` under the **Allowed grant types**.

    :::note
    To enable refresh tokens for the token exchange grant, include `Refresh Token` as an **Allowed Grant Type**. Learn more about [how the refresh token grant type works](../../../../references/iam-concepts/grant-types.mdx#refresh-token-grant).
    :::

4. Click **Update** to save the configurations.

## Token exchange flows

{edition.productName} supports the following token exchange flows.

- **Federated token exchange**: A third-party token issuer issues the subject token. You need to register that issuer as a trusted token issuer.
- **{edition.productName} token exchange**: {edition.productName} issues the subject token.

### Exchange a federated token

{edition.productName} validates the subject token against the trusted token issuer you register for it, and issues a new token for the same identity.

#### Register a trusted token issuer

To exchange a federated token for a token issued by {edition.productName}, you need to register the third-party token issuer as a trusted token issuer in your {edition.productName} organization.

To register a trusted token issuer:

1. On the {edition.productName} console, go to **Connections**.
2. Click **New Connections** and click **Create** on the **Trusted Token Issuer**.
3. Enter the following details of the trusted token issuer:

    | Parameter | Description |
    | --- | --- |
    | Trusted token issuer name | A unique name for the new trusted token issuer. |
    | Issuer | A unique issuer value of the trusted token issuer. This is the value of the \`iss\` claim in the JWT token generated from the configured identity provider. <br /> Example: `https://third-party-token-issuers.io/oauth2/token` |
    | Alias | The name by which the trusted token issuer knows {edition.productName}. The `aud` claim of the token should include the {edition.productName} organization's issuer value. If the `aud` claim doesn't include the organization's issuer value, the system validates the alias value you assign here against the `aud` claim. |

4. Click **Next** and provide the mode of certificate configuration.

    - **JWKS endpoint**: The JWKS endpoint of the trusted token issuer.

        :::note
        For JWKS endpoints, the default read timeout equals 1000 milliseconds. To modify this value, add the following parameter to the `deployment.toml` file in the `<PRODUCT_HOME>/conf/repository` directory.

        ```toml
        [oauth.jwks_endpoint]
        read_timeout = <value in milliseconds>
        ```
        :::

    - **Use PEM certificate**: Upload or paste the public certificate of the trusted token issuer. The certificate should be in PEM format.

        <details>
        <summary>If you have a certificate in other formats such as `.crt`, `.cer` or `.der`, expand here to see how you can convert them to PEM format using [OpenSSL](https://www.openssl.org/)</summary>

        **Convert CRT to PEM**
        ```bash
        openssl x509 -in cert.crt -out cert.pem
        ```
        **Convert CER to PEM:**
        ```bash
        openssl x509 -in cert.cer -out cert.pem
        ```

        **Convert DER to PEM:**
        ```bash
        openssl x509 -in cert.der -out cert.pem
        ```

        </details>

5. Click **Finish** to add the new trusted token issuer.

#### Configure token exchange for a local user

{edition.productName} can exchange a federated token with a token issued for an existing local user account. This is beneficial if you wish to check for blocked/disabled user accounts or to enforce Role-Based Access Control (RBAC).

You can use the following properties to customize how token exchange occurs for identities with local user accounts.

{/* vale WSO2-IAM.TooWordy = NO */}
##### Prioritize local account attributes
{/* vale WSO2-IAM.TooWordy = YES */}

After enabling this configuration, {edition.productName} includes the local user profile information in the exchanged token if the federated identity has a linked local user account. Otherwise, {edition.productName} returns the profile information received directly from the federated identity.

To prioritize linked local account attributes:

1. On the {edition.productName} console, go to **Applications**.

2. Open your application from the list and go to its **User Attributes** tab.

3. Scroll down and under **Attribute Resolution for Linked Accounts**, select **Use linked local account attributes**.

    :::note
    Select **Require linked local account** for {edition.productName} to return an error when it can't find a user account linked to the federated identity.
    :::

##### Implicit account linking

You can use implicit account linking in the registered trusted token issuer to create an account link automatically. The link connects a local user account in {edition.productName} with a federated identity during token exchange.

You can configure lookup attributes to search for a matching local user account. If the system finds a matching account, {edition.productName} automatically links the local user account to the federated identity.

After establishing account links, administrators can't delete them. Users can manage their own accounts links using the [Manage linked accounts](../../../user-self-service/my-account-portal/explore-self-service-features/manage-linked-accounts.mdx) capability in the Self-service portal.

:::warning[Important]
When configuring implicit account linking, select lookup attributes (such as `email`, `username`, or `externalId`) that are unique across all user stores. This prevents failures when multiple accounts match the same attribute.
:::

:::note
{edition.productName} skips implicit account linking when **Require linked local account** is disabled, even if the implicit linking option remains enabled.
:::

You can configure implicit account linking using the
[Implicit Association API](../../../../apis/idp/index.mdx#op-updateImplicitAssociation).

#### Try out federated token exchange

Follow the steps given below.

1. Get the JWT token received from the third-party token issuer.
2. Execute the following cURL command to exchange the federated token for an {edition.productName} token.

    ```bash
    curl --location '{edition.productUrlFormat}/oauth2/token' \
    --header 'Content-Type: application/x-www-form-urlencoded' \
    --header 'Authorization: Basic <base64 Encoded (clientId:clientSecret)>' \
    --data-urlencode 'scope=<desired scopes>' \
    --data-urlencode 'subject_token=<jwt_token>' \
    --data-urlencode 'subject_token_type=urn:ietf:params:oauth:token-type:jwt' \
    --data-urlencode 'requested_token_type=urn:ietf:params:oauth:token-type:access_token' \
    --data-urlencode 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange'
    ```

    :::note
    {edition.productName} only copies the `sub` claim from the token received from the trusted token issuer to the exchanged {edition.productName} token.
    :::

Upon successful execution, you will receive the exchanged token.

### Exchange a locally issued token

{edition.productName} can also exchange a token that is issued by itself. This is beneficial if an application needs a token for a different application or a token with a narrower set of scopes.

Two applications take part in this flow.

- **Subject token application**: The application that received the token needed to be exchanged.
- **Requesting application**: The application that requests the new token. {edition.productName} issues the exchanged token to this application.

The same application can play both roles.

#### Configure the subject token application

The subject token should be a JWT access token that includes the token issuer of your organization in its `aud` claim.

To configure the subject token application:

1. On the {edition.productName} Console, go to **Applications**.

2. Open the subject token application from the list and go to the **Protocol** tab.

3. Under **Access Token**, select `JWT` as the **Token type**.

4. Under **ID Token**, add `{edition.productUrlFormat}/oauth2/token` as an **Audience**.

    :::note
    This step is not required from **update level 7.2.0.44** onwards. See the instructions on [updating WSO2 products](https://updates.docs.wso2.com/en/latest/).
    :::

5. Click **Update** to save the configurations.

#### Try out locally issued token exchange

Follow the steps given below.

1. Get a JWT access token for the subject token application.
2. Execute the following cURL command to exchange the token for a new {edition.productName} token.

    ```bash
    curl --location '{edition.productUrlFormat}/oauth2/token' \
    --header 'Content-Type: application/x-www-form-urlencoded' \
    --header 'Authorization: Basic <base64 Encoded (clientId:clientSecret)>' \
    --data-urlencode 'scope=<desired scopes>' \
    --data-urlencode 'subject_token=<jwt_token>' \
    --data-urlencode 'subject_token_type=urn:ietf:params:oauth:token-type:jwt' \
    --data-urlencode 'requested_token_type=urn:ietf:params:oauth:token-type:access_token' \
    --data-urlencode 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange'
    ```

Upon successful execution, you will receive the exchanged token.

## Delegation

:::note
This feature is available from **update level 7.2.0.44** onwards. See the instructions on [updating WSO2 products](https://updates.docs.wso2.com/en/latest/).
:::

The token exchange grant can also issue a token that preserves the identity of the party acting on behalf of the user. The requesting application presents an actor token along with the subject token, and {edition.productName} records the acting party in the `act` claim of the exchanged token.

For instructions, see [Delegation](../../../authorization/delegation.mdx).

## Request a specific audience

:::note
This feature is available from **update level 7.2.0.44** onwards. See the instructions on [updating WSO2 products](https://updates.docs.wso2.com/en/latest/).
:::

By default, {edition.productName} adds all the audiences registered for the requesting application to the exchanged token. To limit the audience of the exchanged token to a single value, add the `audience` parameter to the token request with the required audience.

The requested audience should be one of the audiences registered for the requesting application. {edition.productName} returns an `invalid_target` error if the request contains more than one audience value, or an audience that is not registered for the application.
