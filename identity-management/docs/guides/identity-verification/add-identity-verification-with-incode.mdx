[Incode](https://incode.com/) is an identity verification platform that verifies a person against a government-issued identity document such as a passport, driver's license, or national ID card, combined with a selfie and liveness detection.

This guide explains how you can use Incode to verify a user's identity when their account gets created in {edition.productName}, and to re-verify the same person with Incode face authentication when they sign in to an application or recover their password.

## Prerequisites

Before you begin, ensure you have the following:

- An Incode account with access to the Incode Dashboard. To get one, contact [Incode](https://incode.com/).

- [{edition.productName} Account](https://asgardeo.io/signup): Access to your {edition.productName} Console with administrative privileges.

## Configure Incode via the dashboard

{edition.productName} connects to Incode through two OpenID Connect (OIDC) clients:

- An **onboarding** client, which verifies users when their accounts get created.
- An **authentication** client, which re-verifies users with face authentication at login and during password recovery.

To create them,

1. On the Incode Dashboard, create the workflow or flow you want to use for onboarding. It must create an identity for the verified person, so that Incode returns the `identity_id` and `auth_overall_status` claims.

2. On the Incode Dashboard, go to **Manage** > **Configurations** and open the **Authorization** tab.

3. Create a new OIDC authorization client for onboarding. Select the onboarding workflow or flow you created, and add the following redirect URI:

    - `https://accounts.asgardeo.io/t/{organization_name}/accounts/register`

4. Create another OIDC authorization client for authentication. Select **Face authentication**, and add the following redirect URIs:

    - `{edition.productUrlFormat}/commonauth`, for login.
    - `https://accounts.asgardeo.io/t/{organization_name}/accounts/recovery`, for password recovery.

5. Take note of the **client ID** and **client secret** of each client, and the **authorization endpoint** and **token endpoint** URLs of your Incode environment.

:::note
If your organization uses a [custom domain](../customizations/branding/configure-custom-domains.mdx), use it in the redirect URIs in place of the default host.

If you configured custom **Self Signup** or **Recovery Portal** URLs in the [advanced branding preferences](../customizations/branding/configure-ui-branding.mdx#advanced-preferences), the flows redirect to those URLs instead. Register them in place of the `/accounts/register` and `/accounts/recovery` redirect URIs:

- The onboarding client needs the **Self Signup** URL for self-registration and the **Recovery Portal** URL for invited user registration.
- The authentication client needs the **Recovery Portal** URL for password recovery.
:::

## Create the Incode attributes in {edition.productName}

{edition.productName} stores the Incode identity ID, interview ID, and onboarding status on the user's profile, and uses the identity ID to link the account to the verified person. Create these attributes before you add the connections, because the connection template maps the Incode claims to them.

1. On the {edition.productName} Console, go to **User Attributes & Stores** > **Attributes**.

2. Under **Manage Attributes**, click **Attributes**, and then click **New Attribute**.

3. Enter `incodeIdentityId` as the **Attribute Name**.

4. Under **Protocol Mappings**, click the edit icon next to **OpenID Connect**, change the value to `identity_id`, and confirm the change.

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-new-attribute.png").default} alt="New attribute for the Incode identity ID" width="600" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

5. Enter an **Attribute Display Name**, for example, `Incode Identity ID`, and click **Finish**.

6. Repeat steps 2 to 5 for the `incodeInterviewId` and `incodeOnboardingStatus` attributes. Keep their generated protocol mappings.

Learn more in [Add custom attributes](../users/attributes/user-attributes/manage-attributes.mdx#add-custom-attributes).

:::note
{edition.productName} links the account to the Incode identity ID through the OpenID Connect attribute `identity_id`, so it must map to the `incodeIdentityId` attribute. An attribute can have only one OpenID Connect mapping. If you already created `incodeIdentityId` with the generated mapping, go to **User Attributes & Stores** > **Attributes** > **OpenID Connect**, delete the generated attribute, and [add an OpenID Connect attribute](../users/attributes/manage-oidc-attribute-mappings.mdx#add-an-openid-connect-attribute) named `identity_id` that maps to `incodeIdentityId`.
:::

## Add Incode as a connection in {edition.productName}

Create one connection for each Incode client, for example, **Incode Onboarding** and **Incode Authentication**. To create a connection,

1. On the {edition.productName} Console, go to **Connections** and click **New Connection**.

2. Select **Incode Identity Verification** from the available templates.

3. Enter the following details:

    | Field | Description |
    | --- | --- |
    | Name | A unique name for the connection. |
    | Client ID | The client ID of the Incode onboarding or authentication client. |
    | Client secret | The client secret of the Incode client. |
    | Authorization Endpoint URL | The authorization endpoint of your Incode environment. |
    | Token Endpoint URL | The token endpoint of your Incode environment. |

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-create-connection.png").default} alt="Create an Incode connection" width="700" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

4. Click **Create**.

5. Repeat the steps for the other Incode client.

## Verify the attribute mappings in {edition.productName}

The template configures the attribute mappings of each Incode connection. To verify them,

1. On the {edition.productName} Console, go to **Connections** and select your Incode connection.

2. Go to the **Attributes** tab.

3. Verify that the Incode claims `auth_overall_status`, `identity_id`, and `interview_id` map to the `incodeOnboardingStatus`, `incodeIdentityId`, and `incodeInterviewId` attributes, and that the **Subject Attribute** is `identity_id`.

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-attribute-mappings.png").default} alt="Attribute mappings of an Incode connection" width="700" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

:::warning
Don't change the subject attribute or the `identity_id` mapping of an Incode connection, and keep just-in-time user provisioning off. If {edition.productName} can't link the account to the Incode identity ID, registration fails with the `INCODE-65011` error.
:::

## Integrate Incode into your flows

The following table summarizes where to add each connection.

| Flow | Connection to add | Placement |
|---|---|---|
| Self registration | Onboarding connection | Before or after the step that collects the user's username and password. |
| Invited user registration | Onboarding connection | Before the step that sets the password. |
| Application login | Authentication connection | A step after the first step that identifies the user, for example, step 2. |
| Password recovery | Authentication connection | After the step that identifies the user. |

In the flow builder, Incode appears as the **Incode Verification** step under **Steps**.

:::note[Only accounts created with Incode are linked]
A user's account gets linked to an Incode identity only when it gets created through a self-registration or invited user registration flow that has the Incode step. Login and password recovery with Incode work only for these users.

Users who existed before you set up Incode, or who registered through a flow without the Incode step, fail with the `INCODE-60001` error at login and the `INCODE-60005` error during password recovery.
:::

### Self-registration

Use this flow to onboard a new user only after Incode verifies their identity.

To configure the flow,

1. On the {edition.productName} Console, go to **Flows** and select **Self Registration**.

2. From **Steps**, add the **Incode Verification** step before or after the step that collects the user's username and password.

3. Select the **Incode Verification** step, and under **Execution Properties**, select your onboarding connection as the **Connection**.

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-self-registration-flow.png").default} alt="Self-registration flow with the Incode step" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

4. Click **Publish** and enable the flow.

When a user registers, the following happens:

1. {edition.productName} redirects the user to Incode onboarding.

2. The user captures their identity document and takes a selfie.

3. Incode redirects the user back to {edition.productName} with the verification result.

4. {edition.productName} checks the result and that no other account is linked to the same identity. It then creates the account with the Incode attributes, and links the account to the Incode identity ID.

The following table lists the possible outcomes.

| Incode result | Outcome |
|---|---|
| Verification accepted, including after a manual review | The account gets created and linked to the identity ID. |
| Verification needs a manual review | Registration fails with the `INCODE-60004` error. |
| Verification failed | Registration fails with the `INCODE-60003` error. |
| The identity is already linked to an account | Registration fails with the `INCODE-60009` error before the account gets created. |
| The user cancelled, or Incode didn't complete the verification | Registration fails with the `INCODE-60002` error. |

:::note
The username the user enters in the flow is kept. Incode doesn't change it.
:::

### Invited user registration

Use this flow when an administrator creates a user account and invites the user. Incode verifies the person who accepts the invitation and links the account to their identity.

To configure the flow,

1. On the {edition.productName} Console, go to **Flows** and select **Invited User Registration**.

2. From **Steps**, add the **Incode Verification** step before the step that sets the password.

3. Select the **Incode Verification** step, and under **Execution Properties**, select your onboarding connection as the **Connection**.

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-invited-user-registration-flow.png").default} alt="Invited user registration flow with the Incode step" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

4. Click **Publish** and enable the flow.

When an invited user accepts the invitation, the following happens:

1. {edition.productName} redirects the user to Incode onboarding.

2. The user captures their identity document and takes a selfie.

3. If Incode accepts the verification, {edition.productName} links the account to the Incode identity ID, stores the Incode attributes, and lets the user set their password.

:::note
- The outcomes are the same as in [self-registration](#self-registration).
- The username the administrator set is kept.
- Incode doesn't compare the identity document with the profile the administrator created. The step verifies the person and links the account.
:::

### Login face authentication

Use this flow to re-verify a linked user with face authentication before they access an application.

To configure the login flow,

1. On the {edition.productName} Console, go to **Applications** and select your application.

2. Go to its **Login Flow** tab.

3. Keep a first step that identifies the user, such as **Username & Password**, with **Pick user identifier from this step** selected.

4. Click **+** to add a second step, click **Add Sign In Option**, and select your authentication connection.

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-login-flow.png").default} alt="Login flow with Incode as the second step" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

5. Click **Update** to save the changes.

When a user signs in, the following happens:

1. After the first step identifies the user, {edition.productName} reads the Incode identity linked to the account and redirects the user to Incode face authentication for that identity.

2. The user completes face authentication.

3. {edition.productName} confirms that Incode verified the same identity. This prevents a user from passing the step with another person's face.

The following table lists the possible outcomes.

| Result | Outcome |
|---|---|
| Incode verified the linked identity | The user signs in. |
| The user cancelled, or Incode didn't verify the user | The application receives the `INCODE-60002` error. |
| Incode returned another error, for example, because the session expired | The application receives the `INCODE-60005` error. |
| Verification failed, or Incode didn't return a result | The application receives the `INCODE-60003` error. |
| Incode verified a different identity | The application receives the `INCODE-60008` error. |
| The request to Incode failed, for example, because of a wrong client secret | The application receives the standard `login_required` error. |
| The account isn't linked to an Incode identity | Login stops on an error page with the `INCODE-60001` error, before the user goes to Incode. |

The application receives these errors at its redirect URL as a standard OAuth 2.0 error response. The `error` parameter carries the error code and the `error_description` parameter carries a message that you can show to the user, for example, with an option to sign in again. If the login flow has a conditional authentication script, it can handle the failure in `onFail`.

:::note
- The Incode step must come after a step that identifies the user, and the user identifier must come from that earlier step. Otherwise, login stops on an error page with the `INCODE-65001` or `INCODE-60010` error.
- The login step doesn't link accounts.
- You don't need a conditional authentication script for this flow.
:::

### Password recovery

Use this flow to prove that the person resetting the password is the account holder.

To configure the flow,

1. On the {edition.productName} Console, go to **Flows** and select **Password Recovery**.

2. From **Steps**, add the **Incode Verification** step after the step that identifies the user.

3. Select the **Incode Verification** step, and under **Execution Properties**, select your authentication connection as the **Connection**.

    <img src={require("../../../assets/cloud/img/guides/identity-verification/incode/incode-password-recovery-flow.png").default} alt="Password recovery flow with the Incode step" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

4. Click **Publish** and enable the flow.

When a user recovers their password, the following happens:

1. {edition.productName} reads the Incode identity linked to the account and redirects the user to Incode face authentication for that identity.

2. The user completes face authentication.

3. {edition.productName} confirms that Incode verified the same identity and lets the user reset their password.

:::note
- This flow is an identity check only. {edition.productName} doesn't change the profile or the link.
- Accounts that aren't linked fail with the `INCODE-60005` error without being redirected to Incode. In the example above, the Incode step directly follows the step where the user enters their username. To avoid revealing whether an account is linked, add a step that verifies the user, such as an emailed link or code, before the Incode step.
:::

## Reference

The following sections provide more details on how {edition.productName} works with Incode.

### How it works

{edition.productName} connects to Incode as a federated OpenID Connect connection.

- When a user's account gets created, {edition.productName} redirects the user to Incode, where they capture their identity document and take a selfie. Incode returns the verification result and an **identity ID** that identifies the verified person.

- {edition.productName} creates the account only if Incode accepts the verification, and links the account to the Incode identity ID.

- Later, when the user signs in to an application or resets their password, {edition.productName} redirects them to Incode face authentication for the identity linked to their account. The step succeeds only if Incode verifies the same identity.

The two Incode connections have the following roles.

| Connection | Purpose | Used in |
|---|---|---|
| Onboarding connection | Verifies users and links their accounts when the accounts get created. | Self registration, invited user registration |
| Authentication connection | Re-verifies linked users with face authentication. | Application login, password recovery |

### Account linking

When a user completes the Incode step in the self-registration or invited user registration flow, {edition.productName} stores the Incode identity ID as a federated association of the user, against the onboarding connection. Login and password recovery use this association to identify the user at Incode, even though they use the authentication connection.

Users can't create or change this association.

:::warning
The `incodeIdentityId`, `incodeInterviewId`, and `incodeOnboardingStatus` attributes are for display only. Users can update their profile attributes, so don't use these attributes for authorization decisions. {edition.productName} itself relies only on the association.
:::

### Authorization request parameters

At login and during password recovery, {edition.productName} extends the standard OIDC authorization request with the following parameters.

| Parameter | Value |
|---|---|
| `login_hint` | The Incode identity ID linked to the account. |
| `prompt` | `login` |

{edition.productName} handles the token exchange, `state`, and claim mapping in the same way as any other OIDC connection.

### Limitations

- **Linking through registration.** Accounts get linked during self-registration or invited user registration. Existing accounts can't be linked through a flow; an administrator can add the link through the user federated associations API.

- **Supported flow types.** The **Incode Verification** step is only available in the self-registration, invited user registration, and password recovery flows. For login, add the authentication connection to the application's login flow.

- **Duplicate check per organization.** {edition.productName} refuses an identity that is already linked through any Incode connection of the organization. The same identity can register once in each organization.

- **Sub-organizations.** Registration and password recovery in a sub-organization redirect to the sub-organization's own `/accounts/register` and `/accounts/recovery` URLs, for example `.../t/{root-organization}/o/{sub-organization-id}/accounts/register`. If you share the Incode connections with sub-organizations, register these URLs on the Incode clients as well. Login doesn't need an extra redirect URI.

- **App-native authentication.** The Incode login step doesn't support app-native authentication.

- **Results on redirect only.** {edition.productName} receives the verification result when Incode redirects the user back. It can't pick up a verification that completes later, for example, after a manual review.

### Error codes

The following are the common errors you may encounter.

| Error code | Description |
| --- | --- |
| `INCODE-60001` | The account isn't linked to an Incode identity. |
| `INCODE-60002` | The user cancelled the verification, or Incode didn't complete it. Incode reports both the same way. |
| `INCODE-60003` | The verification failed. |
| `INCODE-60004` | The verification needs a manual review. |
| `INCODE-60005` | The verification couldn't be completed. During password recovery, this also means the account isn't linked to an Incode identity. |
| `INCODE-60007` | The verification response is invalid or expired. |
| `INCODE-60008` | Incode verified a different identity than the one linked to the account. |
| `INCODE-60009` | The identity is already linked to another account. |
| `INCODE-60010` | No user was identified before the Incode login step. |
| `INCODE-65001` | The user identifier comes from the Incode login step instead of a step before it. |
| `INCODE-65004` | The OpenID Connect exchange with Incode failed during registration or password recovery. |
| `INCODE-65009` | The Incode response doesn't include an identity or a verification result. |
| `INCODE-65010` | The Incode identity linked to the account couldn't be read. |
| `INCODE-65011` | The account couldn't be linked to the Incode identity ID. |

### Troubleshooting

| Symptom | Cause |
|---|---|
| Registration fails with the `INCODE-65011` error. | The OpenID Connect attribute `identity_id` is missing or doesn't map to `incodeIdentityId`, or the subject attribute or attribute mappings of the connection were changed. |
| Registration fails with the `INCODE-65009` error. | The onboarding workflow or flow selected on the Incode onboarding client doesn't create an identity. |
| Login fails with the `INCODE-60001` error. | The user registered through a flow without the Incode step. |
| Incode rejects the `login_hint`. | The Incode authentication client doesn't use **Face authentication**. |
| Incode shows a redirect URI error. | The redirect URIs registered on the Incode client don't match the ones listed in [Configure Incode via the dashboard](#configure-incode-via-the-dashboard). |
